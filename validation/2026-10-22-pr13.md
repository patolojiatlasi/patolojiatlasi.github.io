## Build method and environment

The established local entry points are `Rscript R/render_TR.R` and `Rscript R/render_EN.R`. The combined GitHub workflow also commits and deploys outputs, so it was not triggered.

This sandbox initially had neither R nor Quarto. Validation used an isolated R 4.3.3 runtime and Quarto CLI 1.8.27, with rmarkdown 2.25, knitr 1.45, yaml 2.3.12, xml2 1.3.6 and qrcode 0.3.0. The CI workflow specifies R 4.3.0 and a floating Quarto pre-release; this is not a claim of exact CI environment parity.

The R `quarto` package could not be installed: `processx` failed to load because `ps::ps_handle()` could not read this sandbox's own process information (`No such file or directory`). Both unmodified R entry-point attempts therefore stopped at `quarto::quarto_render` with the package unavailable. The supported CLI fallback executed exactly the preparation prefix of each existing script, then ran `quarto render` in that edition's isolated copy:

```sh
# From a fresh isolated source copy, with R and Quarto available:
# TR; use R/render_EN.R in the second copy for EN.
Rscript -e 's <- readLines("R/render_TR.R"); i <- grep("^quarto::quarto_render", s)[1]; eval(parse(text = s[seq_len(i - 1)]))'
quarto render
```

This preserves the existing language/configuration setup, English chapter/include preparation, Quarto pre-render hooks and SEO post-render hook. It omits the R scripts' post-render deployment-directory copying. Initial fresh executions also exposed the missing declared `qrcode` dependency; after installing it, both complete CLI builds succeeded. Successful full-build logs contained no `WARN`, `WARNING`, `Error` or `ERROR` entries.

After applying the appendix correction to the TR build copy, `quarto render` ran over the entire book again (unchanged execution could use that copy's newly generated cache). This final full render, rather than a focused single-page render, regenerated the full sitemap and search index.
